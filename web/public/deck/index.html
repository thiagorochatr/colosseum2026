Alibi

Private payments that keep the issuer’s rules.

Solana · Tempo · one zero-knowledge proof

Problem

Solana’s privacy pools screen once, at the door

Checked at deposit

Pools screen a deposit through an off-chain API, once, when it arrives.

Flagged later, still exits

Funds flagged after they were deposited withdraw like any others.

Nothing to show

Nothing on chain tells a partner that a withdrawal came from clean funds.

That gap stands between these pools and exchanges, offramps and institutions.

The idea

Prove your deposit is clean, without saying which one is yours.

The check runs at withdrawal, against the rule in force.

How it works

Four steps, one proof

1

Deposit

A fixed amount, with a commitment to secrets that stay in the browser.

2

Clean set

A second tree holds the same deposits, minus those the policy blocks.

3

Prove

The browser proves the deposit is in both trees, bound to one recipient.

4

Pay

The chain checks the proof, and the money goes to a fresh address.

Blocked after depositing? The deposit leaves the clean set, and no valid proof exists for it.

On Solana

Compliance as a layer any pool can require

A public clearance

A compliance program verifies the proof and writes an account any program can check.

mirror-pool, unchanged

The reference pool is wrapped byte for byte, with one added instruction: a spend tied to a clearance.

An auditable curator

A pluggable role. Its policy hash is on chain, and it can only remove deposits, never add one.

proof → compliance program → clearance account → pool pays

On Tempo

The same proof, under the issuer’s own policy

No new trust

The clean set comes from the issuer’s TIP-403 policy, on chain. Anyone can apply it, no one can bend it.

No race

The issuer can block an address and exclude its deposits in one batch transaction.

No owner

The pool cannot be upgraded or paused by anyone.

one circuit · one verifying key · both chains
